# 树形对话工作台 — 设计文档

**日期**：2026-08-05
**状态**：设计已确认，待用户最终审阅

## 1. 背景与问题

和 AI 对话时，一个回答往往内容丰富。当用户想基于其中某个点展开深入讨论，讨论完再想回到"最初那个分支点的上下文"继续时，在传统线性会话里回不去了——上下文已经被后续讨论覆盖/推远。

本项目要解决的核心是**上下文管理**：让"发散探索"和"回到原分支继续"都成为一等操作。做法是把对话本身建模成一棵**树**——在任意点发散会生成子节点（带着那个点的上下文），探索完可回到父节点继续，必要时把子分支的结论合并回父节点。整体做成一个**本地 web 工具**，交互设计是成败关键。

## 2. 核心概念模型（地基）

四个核心概念，后续所有交互与代码都基于此词汇：

- **Tree（树 / 文档）**：一次完整探索的顶层容器。可有多棵树对应多个主题。**树就是文档**。
- **Node（节点）**：树上的一个单元，代表"一轮对话回合"（一条用户输入 + 一条 AI 回复）。是文档的一个"块"。每个节点有唯一父节点（根除外），可有多个子节点（= 多个分支）。**node ≈ 一篇文档**。
- **Annotation（批注）**：挂在某节点 AI 回复正文上的锚点。两种：`selection`（选中一段文字）、`whole`（针对整条消息）。一个批注可"长出"一个子节点，也可只是笔记。**同一节点可有多个批注 → 多个并行分支。**
- **ContextSegment（上下文段）**：本设计的灵魂。节点调用 AI 时，其上下文由一个**有序的"段"列表**组装而成。段类型：
  - `ancestor-full`：某祖先节点的完整问答原文（引用式，不复制正文）
  - `ancestor-summary`：某祖先的摘要（v2 长对话优化时才启用）
  - `annotation-seed`：分叉时选中的那段批注文字 + 用户追问（"我想深入聊这个"的引子，快照）
  - `merged-conclusion`：从子分支合并回填进来的结论（快照）

**近期上下文组装策略（唯一）**：把根→父的所有节点作为 `ancestor-full` 段 + 当前节点的 `annotation-seed` 段，按顺序拼接发给 AI（等价于"完整前缀"）。未来省 token 只需换组装策略，把远处祖先替换成 `ancestor-summary`，**数据结构不改**。

**为什么这样设计**：分叉、合并、节点版本三件事最终都归约为"对某节点的 ContextSegment 列表做增删改"，共享同一抽象，后续不打架。

## 3. 数据模型（SQLite）

### trees
`id` (pk) · `title` · `created_at` · `updated_at` · `root_node_id`

### nodes
`id` (pk) · `tree_id` (fk) · `parent_id` (fk, 可空=根) · `sort_order`
· `user_input` · `ai_response`（ProseMirror JSON，用于挂批注锚点）
· `status`（`draft`/`streaming`/`complete`/`error`）
· `is_deleted`（软删除标记）
· `model_override`（可空，预留：某节点单独指定模型；v1 不用但零成本预留）
· `created_at` · `updated_at`

> **Provider/模型不挂在 node 上**，放全局配置。

### annotations
`id` (pk) · `node_id` · `kind`(`selection`/`whole`)
· `anchor_from` · `anchor_to`（ProseMirror 位置；`whole` 为空）
· `quoted_text`（选中原文快照，防锚点漂移丢引子）
· `note`（用户批注文字，可空）· `child_node_id`（长出的子节点，可空=仅笔记）
· `created_at`

### context_segments
`id` (pk) · `node_id` · `seq`（顺序）
· `type`（`ancestor-full`/`ancestor-summary`/`annotation-seed`/`merged-conclusion`）
· `ref_node_id`（type 为 ancestor-* 时指向祖先，可空）
· `ref_version_no`（可空；留空=跟随该祖先**最新**版本，指定=**锁定**到某历史版本）
· `content`（type 为 seed/summary/merged-conclusion 时存快照文字，可空）

> `ancestor-full` 段不复制正文，运行时按 `ref_node_id`(+可选 `ref_version_no`) 取祖先内容——父被编辑时子上下文默认自动跟随最新；用户可点开某祖先段锁定到特定历史版本。`annotation-seed`/`merged-conclusion` 存快照文字（是"当时那句话"，不随父变）。

### node_versions（节点级内容历史）
`id` (pk) · `node_id` · `version_no`（递增）
· `user_input` · `ai_response`（该版本内容快照）
· `change_kind`（`edit`/`merge`/`regenerate`）· `created_at`

> 每次编辑内容/合并回填/重新生成写一条快照。diff/回退在同一 `node_id` 相邻 `version_no` 间进行。**只增不减**。

### merges（合并可追溯记录）
`id` (pk) · `source_node_id`（被合并的子分支根）· `target_node_id`（回填到的父节点）
· `conclusion`（提炼结论文字）· `landing_segment_id`（落到父节点的哪个 context_segment）
· `created_at`

> 合并**不删子分支**，只在父节点加 `merged-conclusion` 段 + 记 merge。子树永远可展开回看。

### settings / provider_config（全局）
默认 provider、模型、密钥引用等。v1 默认 Codex，架构做成 Provider 可插拔。

### 关键设计决定
1. AI 回复存 **ProseMirror JSON**（非纯文本），以精确挂批注锚点。
2. 合并**不销毁子树**，只加段 + 记录。
3. 节点版本存**内容快照**，diff 在相邻版本间实时计算，不存 diff 本身。
4. 删除采用**软删除**（`is_deleted` 标记，可恢复，数据永不物理删），配"回收站/已隐藏"视图。

## 4. 核心数据流

### ① 提问 / 回答（生成节点）
1. 用户在某节点输入框提问 → POST 后端。
2. 后端读该节点 `context_segments`，用当前组装策略拼出消息数组（`ancestor-full` 按 `ref_node_id`(+`ref_version_no`) 取祖先内容，加 `annotation-seed`/`merged-conclusion` 文字，按 seq 排序）。
3. 调 Provider（Codex），**流式**（SSE）推回前端；`status` `streaming`→`complete`。
4. 回复以 ProseMirror JSON 落库到 `nodes.ai_response`。

### ② 批注
1. 选中 AI 回复中一段 → 记 ProseMirror `from/to` + 原文。
2. 弹批注气泡：写笔记 / 直接"就此展开" / 删除。
3. 存 `annotations`（带锚点 + `quoted_text`）。`whole` 批注同理。
4. 同一节点可挂多条批注 → 多个高亮，各自可展开。

### ③ 分叉（从批注长出子节点）
1. 在批注上点"展开" + 输入追问。
2. 新建 `nodes`（`parent_id`=当前），回填 `annotations.child_node_id`。
3. 组装子节点 `context_segments`：根→父路径每个节点一个 `ancestor-full` 段（默认跟随最新版本）+ 一个 `annotation-seed` 段（`quoted_text` + 追问）。
4. 子节点按 ① 流程对话——带着"完整来龙去脉 + 那个具体点"。

### ④ 回溯（回到父节点继续）
1. 点面包屑任意一级 / 点树中任意节点 → 切换"当前节点"。
2. 该节点对话原样恢复，可继续追问。**这是核心痛点的解法：任何分叉点随时可回、可续。**

### ⑤ 合并（子分支结论回填父节点）
1. 在探索完的子分支点"合并回父节点"。
2. 后端把子分支对话喂 AI 提炼结论（v1：整段落到分叉点；v2：拆多条 + 建议落点，逐条确认）。
3. 父节点插入 `merged-conclusion` 段；写一条 `node_versions`(`change_kind=merge`)；记一条 `merges`。
4. 子分支**不删**，树上标"已合并"，可展开回看。
5. 之后父节点对话即带上该结论。

## 5. 交互设计（成败关键）

### 5.1 布局：最多三栏，角色动态滚动
```
┌──────────┬─────────────────────┬─────────────────────┐
│ 树导航    │  主文档 (当前工作文档) │  子文档 tabs (派生)   │
│ (全局地图)│                     │  [tab1][tab2][tab3] │
│ ▾ 根      │  # 缓存层设计        │  # Redis 深入        │
│  ▾ 主文档 │  正文... ▓批注▓...   │  正文...            │
│    ⎇Redis│  ┌批注: 就此推进↳┐   │  [聚焦此文档 ⤢]     │
│    ⎇内存  │  └───────────────┘   │                     │
│  ✓已合并  │  ┌─对话框────────┐   │  ┌─对话框────────┐  │
│          │  │ 继续提问...   │   │  │ 继续提问...   │  │
│          │  └───────────────┘   │  └───────────────┘  │
└──────────┴─────────────────────┴─────────────────────┘
```
- **左栏**：可折叠树导航（全局地图，永远在）。有分支的节点标 `⎇`；已合并分支标 `✓已合并` 置灰但可展开；软删除项进"回收站"视图。
- **中栏**：当前主文档（正在读/续写的那篇，可纵向叠多篇 node）。AI 回复为 ProseMirror 富文本，批注处彩色高亮。选中文字浮出批注气泡。底部对话框继续追问。
- **右栏**：从主文档派生的子文档 **tabs**（一次显示一篇，顶部多 tab 切换）。每篇有"聚焦"按钮。

**动态角色**：中栏永远是"当前工作文档"，右栏永远是"从它派生的待处理分支 tabs"，左栏永远是全局地图。

**沉浸聚焦模式**：可切换隐藏树栏、专注当前文档；顶部面包屑 + 前进/后退回溯。

### 5.2 三栏行为
- **展开多篇子文档**：右栏用**标签页**容纳，顶部一排 tab，一次显示一篇。
- **聚焦某子文档 = 晋升**：该子文档移到中栏成为新主文档，右栏刷新成它自己的子分支 tabs。栏位角色向前滚动，始终维持"树｜主｜子"三栏。
- **回溯**：面包屑/左栏点击让某祖先文档重新晋升回中栏（右栏随之变其子分支）；前进/后退键在最近访问文档间跳。

### 5.3 三种推进方式
1. **批注推进**：批注某点 → "推进" → 右栏新开子文档 tab（AI 就该点作答）。
2. **对话框直接提问**：底部对话框问 → 触发**并行路由**决定落点（见 5.4）。
3. **聚焦晋升**：点子文档 tab 的"聚焦" → 晋升为中栏主文档。

### 5.4 并行路由（v1 核心亮点）
用户底部提问时，后端**并发**两件事（无数据依赖）：
1. **作答请求**：乐观地按"当前主文档延续"**立即**流式作答（零等待，字即刻蹦出）。
2. **路由判定请求**：轻量判定该问题归属何处——输入 = 问题 + 主文档结构大纲（各段/已展开子文档的标题或摘要，非全文，省 token 快返回）；输出 = 候选落点列表 + 各自置信度。落点三类：`当前主文档延续` / `绑定到已展开子文档X` / `从主文档某段Y新开分支`（**Y 可以是尚未展开/未批注的段** —— 系统识别"这问题其实对应主文档某段"就地开新分支）。

**置信度收敛规则（C 策略）**：
- 最高分 ≥ 高阈值且明显甩开第二名 → 直接在该落点作答（若与乐观假设一致则无感；不一致则弹轻提示"这轮更像在深入【X】，搬过去？"，一键迁移）。
- 分数不够高 / 前两名咬得紧（模糊）→ 弹候选面板列 top 2-3 落点 + "都不对，接主文档下"，用户一键选后迁移。
- 阈值先设默认值、做成可调，跑一阵看手感再调。

```
发送问题 ──┬──► [作答] 立即流式答在主文档 ──────────► 内容已生成
           │                                          │
           └──► [路由判定] ──► 一致: 无操作            │
                             ├─ 高置信指向别处: 提示"搬到X?" → 一键迁移 ◄┘
                             └─ 模糊: 弹候选面板 → 用户选 → 迁移
```

**迁移策略 = 改挂不重答**：迁移只改 node 的 `parent_id` 和 `context_segments` 归属，**不重新生成内容**。理由：主文档延续的上下文是超集，搬到子分支只是背景更全，信息只多不少，回答不会因此变错。

**路由判定失败**：判定是锦上添花，失败**不阻塞作答**，静默降级为"留在主文档"，不打扰用户。

### 5.5 多文档聚合（v2）
中栏出现多篇文档后，可让 AI 把它们**聚合**成一篇，结果**必须人工 review** 后才算数（本质是"合并"的加强版：从单分支回填升级为多文档聚合，与 v2 智能合并落点同属"AI 提炼、人工确认"能力）。

## 6. 错误处理 & 边界

- **流式作答中断/超时**：`status=error`，已收部分保留并落库，显示"继续生成/重试"（用同样上下文段重调）。
- **路由判定失败**：不阻塞作答，静默降级留主文档。
- **Provider 密钥无效/额度耗尽**：明确报错 + 指向设置页，不吞错、不假装成功。
- **锚点漂移**：父文档编辑后选区 `from/to` 可能失效；用 `quoted_text` 快照兜底——界面标"原文已变动"并用快照显示当初锚定内容，分支上下文照常用快照，不丢引子。
- **重复合并同一分支**：允许，提示"已合并过"，生成新 `merged-conclusion` 段（不覆盖旧），历史全留。
- **版本回退**：回退 = 写新版本（内容=旧版内容，`change_kind=edit`），非删除，只增不减。
- **删除有子分支的节点**：软删除（隐藏、可恢复），子树数据保留；不物理删。
- **循环/孤儿**：分叉只能向下建子，天然无环；软删除父节点其子树跟随隐藏但不失联。

## 7. 技术栈

- **前端**：Vite + React + TypeScript（交互密集，树/拖拽/富文本生态全）
- **富文本/批注**：TipTap / ProseMirror（选区-锚点-批注是其强项，对上"评论式展开"）
- **后端**：Node + Fastify + TypeScript（与前端同语言，本地服务轻量）
- **存储**：SQLite（单人本地，天然适合树结构 + 节点版本历史）
- **AI Provider**：默认 Codex；架构做成 **Provider 可插拔**（后端一层抽象，未来切 Claude/OpenAI/内部网关）；全局配置。
- **传输**：SSE 用于流式作答。

## 8. 测试策略

按风险倾斜投入，核心数据正确性逻辑**与 AI 解耦**（用 mock provider）：
- **上下文组装（最高优先级）**：给定树 + 节点 → 组装出的段序列正确，覆盖完整前缀、`ref_version_no` 锁版本、含 `merged-conclusion`/`annotation-seed` 段。
- **合并逻辑**：合并后"父加段 + 版本记录 + merge 记录 + 子树保留"四件事都发生且可追溯。
- **节点版本/diff/回退**：只增不减、回退语义、相邻版本 diff 正确。
- **路由收敛逻辑**：把"判定结果 → 落点收敛/迁移"纯逻辑抽出单测（给定判定输出，迁移改挂正确的 parent/segments）；AI 判定质量靠少量人工 eval。
- **Provider 抽象**：mock provider 测流式/错误/超时路径，不依赖真 Codex。
- **前端交互**：三栏角色滚动、聚焦晋升、批注锚点、面包屑回溯——组件测 + 少量 e2e。

原则：数据正确性核心逻辑重点自动化测且与 AI 解耦；AI 输出质量靠人工 eval，不硬塞进自动化测试。

## 9. 分期交付

### v1（首期，先 run 起来）
三栏布局 + 树/节点 CRUD + 批注分叉 + 完整前缀上下文组装 + 流式作答 + **并行路由（含 C 置信度弹选 + 一键迁移）** + 单分支合并回填 + 节点版本/diff/回退 + 软删除（回收站视图）+ Codex Provider + 全局 Provider 配置 + 沉浸聚焦模式 + 面包屑/前进后退回溯。

### v2（首期，智能增强）
- 合并时 AI 拆多条结论 + 建议多落点、逐条确认。
- 多文档 AI 聚合 + 人工 review。
- 长对话时切换"祖先摘要"组装策略省 token（启用 `ancestor-summary` 段）。

> v1 + v2 均纳入首期实现范围。

### v3（未来可扩展方向，仅记录，不列入首期）
- 无限画布 / 思维导图式全局地图视图（节点为画布卡片，缩放平移）。
- 多 Provider 切换 UI（Claude / OpenAI / 内部网关）。
- 跨设备 / 云端账号同步。
- 树级快照/版本（整树某时刻存档、对比、恢复）——当前版本管理只做到节点级。
- 批注/分支的协作与分享（多人 review）。
